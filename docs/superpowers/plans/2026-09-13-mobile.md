# Mobile client implementation

## Scope and architecture

The requested iOS/Android experience continues the desktop client's existing-server
model. Improve the shared responsive interface and provide small native applications
that load the configured HTTPS origin. Reuse same-origin sessions and Socket.IO;
do not introduce a CORS/authentication rewrite or a privileged JavaScript bridge.

## Implementation

1. Preserve existing touch navigation and message actions. Add software-keyboard
   viewport sizing, safe-area handling, landscape support and touch Enter policy.
2. Verify shared behavior with pure input/viewport tests and actual WebKit/Chromium
   browser workflows, including a desktop Enter regression control.
3. Build Android Kotlin/WebView project with origin policy, native setup/navigation,
   microphone/camera permission mediation, document picker and authenticated bounded
   download. Add Gradle wrapper integrity, unit tests, lint and debug packaging.
4. Add iOS UIKit/WKWebView project generated by XcodeGen, per-origin persistent data
   stores, setup/navigation, media permissions and WebKit download/share handling.
   Add origin policy tests and macOS simulator CI.
5. Document installation, release signing and native features requiring later work.
   Validate locally where tooling exists; explicitly distinguish iOS source review
   and browser emulation from a native simulator/device build.

## Acceptance boundaries

Users can configure their existing server and use the common messaging interface.
Phone Return must not send a draft accidentally. The send control must remain
reachable when the software keyboard reduces the viewport, including landscape.
Cross-origin navigation and downloads must not receive server session cookies.
No automatic store publication, background push, native background calling or
screen broadcast is claimed in this implementation.
